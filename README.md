# 本地制品准入校验流程（Artifact Admission Gate）

一套完全在本地运行、可离线复现的制品准入校验系统，用内存中的 ed25519
密钥与 SHA-256 摘要模拟「已签名的构建制品 + 签名溯源链 + SBOM 软件成分信息」，
在不同**签名状态、策略版本、角色权限**下给出**一致且可解释**的放行结论。

仅使用 Go 标准库（`crypto/ed25519`、`crypto/sha256`、`encoding/json` 等），
无任何外部依赖，不需要网络。

## 目录结构

```
internal/model/       共享类型：制品、溯源语句、SBOM、版本化策略、判定、审计记录
internal/signer/      本地 ed25519 签名/验签身份与可信公钥环（KeyRing）
internal/provenance/  制品/溯源链/SBOM 的构造（Builder）与密码学校验（Verifier）
internal/policy/      只增不改的版本化策略存储、时点生效查询、回滚、纯函数规则判定
internal/authz/       基于角色的最小权限矩阵
internal/audit/       只追加、序号稠密、并发安全的审计日志
internal/gate/        无状态、确定性的准入判定流水线
internal/app/         门面：RBAC 鉴权 → 策略快照 → 判定 → 审计
internal/testutil/    确定性签名测试夹具（制品、三级溯源链、SBOM、v1/v2 策略）
cmd/demo/             端到端离线演示
```

## 准入规则

准入判定是一条**短路、首错即停**的流水线，因此每个输入只会命中唯一一个、
互相可区分的拒绝原因：

| 顺序 | 检查阶段 | 通过条件 | 拒绝原因码 |
|----|----------|----------|------------|
| 1 | 制品签名存在性 | `Signature` 非空且带签名者 KeyID | `SIGNATURE_MISSING` |
| 2 | 制品签名有效性 | 用 KeyRing 中登记的公钥可验证「对已签名摘要的签名」 | `SIGNATURE_INVALID` |
| 3 | 内容完整性 | 已签名摘要 == 当前内容的 SHA-256 摘要 | `CONTENT_TAMPERED` |
| 4 | 溯源链存在性 | 至少有一条溯源语句 | `PROVENANCE_MISSING` |
| 5 | 溯源链完整性 | 见下方「溯源链语义」 | `PROVENANCE_BROKEN` |
| 6 | SBOM 存在与绑定 | SBOM 存在、绑定到本制品、其摘要被签名链引用 | `SBOM_MISSING` |
| 7 | 策略符合性 | 见下方「策略规则」 | `POLICY_NOT_SATISFIED` |
| — | 全部通过 | — | `ADMITTED`（ALLOW） |

注意三类失败的区分：**无签名**是没签名；**签名无效**是密码学验签失败；
**内容篡改**是签名仍然有效，但签名所承诺的摘要与当前内容不符（说明内容在
签名之后被改动）。

### 溯源链语义

链是一条有序的签名语句列表（受 in-toto 启发的简化模型）：

- 第 1 条语句的 `SubjectDigest` 必须等于被验制品摘要；
- 每条语句的签名覆盖其规范化 JSON（主体、构建者、步骤、材料列表，含
  材料上的 `Root` 标记）；
- 每条非末级语句必须至少消费一个「由后续某条语句产出」的材料，沿链向
  源头方向行走；任何非根、非 SBOM、且无法解析到后续语句主体的材料即断链；
- 标记 `Root: true` 的材料（如可信基础镜像、源码 tar 包）不需要继续向上
  证明，该标记受签名保护，伪造标记会因语句签名失效而被拒绝；
- SBOM 以名为 `sbom.json` 的附件材料挂在第 1 条语句上，其摘要必须与
  提交的 SBOM 规范化编码摘要一致。

删除一条溯源语句（其余签名全部保持有效）会使前一条语句的材料无法解析，
从而得到 `PROVENANCE_BROKEN`，这正是「溯源断链」与「签名被破坏」的区别。

### 策略规则

策略为不可变的版本化对象，当前包含四条确定性规则（违反时逐条给出
`allowed-builders` / `min-chain-length` / `allowed-licenses` /
`denied-packages` 违规明细）：

1. `AllowedBuilders`：制品的直接构建者必须在允许列表内；
2. `RequiredMinChainLength`：已验证溯源语句数不得少于下限；
3. `AllowedLicenses`：SBOM 中每个组件的许可证必须在白名单内；`"*"`
   表示接受任何**已声明**的非空许可证；
4. `DeniedPackages`：SBOM 不得包含黑名单组件。

策略判定是**纯函数**：同样的策略快照 + 同样的输入，必然得到逐条一致、
顺序稳定的违规列表。

## 策略版本与回滚语义

- 策略只增不改：`Publish` 要求版本号严格递增，已发布的策略内容永不被改写。
- 每条策略带 `EffectiveFrom` 生效时间；`EffectiveAt(t)` 返回在时间点 `t`
  生效的策略（不晚于 `t` 的最近一次生效）。
- `Rollback(v)` **不删除、不修改历史**，只是追加一条「自此刻起版本 v 生效」
  的生效记录。因此：
  - 回滚后，同一输入在当前判定中复现历史版本的结论；
  - 用 `ReplayAt(req, t)` 仍可复现任意历史时点命中的策略版本与结论；
  - 回滚后发布新版本，版本号仍须大于历史上最大版本号（旧号不可复用）。
- 并发安全：每次 `Admit` 先对当前生效策略做快照，再调用无状态 Gate 判定；
  判定结论只依赖请求与快照，与 goroutine 调度顺序无关。并发 400 次混合
  批次（好/篡改制品各半）得到固定的 200 ALLOW / 200 DENY，且原因码稳定。

## 角色权限边界（最小权限）

| 权限 | admin | operator | viewer | anonymous |
|------|:-----:|:--------:|:------:|:---------:|
| `artifact:admit` 提交准入 / 历史复现 | ✗ | ✓ | ✗ | ✗ |
| `policy:read` 读取当前与历史策略 | ✓ | ✓ | ✓ | ✗ |
| `policy:write` 发布新策略版本 | ✓ | ✗ | ✗ | ✗ |
| `policy:rollback` 回滚策略 | ✓ | ✗ | ✗ | ✗ |
| `audit:read` 读取审计记录 | ✓ | ✓ | ✗ | ✗ |

- 越权请求在触碰任何有状态操作**之前**即被拒绝，返回
  `ErrPermissionDenied`；**不改变策略状态、不追加审计记录**（有测试断言
  越权前后审计条数与策略历史完全不变）。
- admin 默认不能提交准入（职责分离）；anonymous 无任何授权。

## 审计追溯

每次准入（无论 ALLOW / DENY）与每次策略发布、回滚都写入只追加日志：

- `Seq` 为全局稠密递增序号，提供跨并发写入者的全序；
- 记录操作、角色、操作者、命中的策略版本、制品摘要、判定结论、原因码与
  文字依据；
- 历史复现 `ReplayAt` 是只读操作，不写审计。

## 本地离线验证方法

需要 Go 1.25+（开发环境为 1.26），无需联网、无需下载依赖：

```bash
# 编译
go build ./...

# 全部单元测试（会打印输入、命中策略版本与判定依据）
go test ./... -v

# 带竞态检测（覆盖并发批次、并发审计写入）
go test -race ./...

# 端到端演示：可区分拒绝原因、v1→v2 演进、历史复现、回滚、并发批次、越权
go run ./cmd/demo
```

### 测试覆盖的关键场景

- **篡改**：签名有效但内容被改 → `CONTENT_TAMPERED`，且与无签名、验签失败
  原因稳定可区分（`internal/provenance`、`internal/gate`、`internal/app`）。
- **溯源断链**：删除中间语句导致材料无法解析、语句签名被破坏、首条语句
  主体不匹配、伪造根材料标记 → 一律 `PROVENANCE_BROKEN` 且细节不同。
- **越权**：viewer/anonymous 提交准入、operator 发布/回滚策略、viewer
  读审计均被拒，且状态零变化（`TestUnauthorizedRequestsDoNotChangeState`）。
- **并发校验**：32 worker × 20 次混合并发准入，结论数与原因码固定，
  审计序号稠密无重号（`TestConcurrentBatchConclusionsAreOrderIndependent`）。
- **版本演进与回滚**：同一签名制品在 v1 放行、v2 因许可证拒绝；按 v1 时代
  时点复现得到历史 ALLOW；回滚后实时结论与复现一致，且审计动作顺序严格
  可追溯（`TestPolicyEvolutionRollbackAndHistoricalReproduction`）。

## 设计上如何保证「一致且可解释」

1. **唯一原因码**：流水线首错即停，拒绝原因互斥、稳定、机器可读。
2. **确定性**：ed25519 签名本身确定；判定为纯函数；集合类输出排序后生成；
   每次判定记录命中的策略版本，不受并发顺序影响。
3. **可复现**：策略只增不改 + 生效时间表，历史结论可按时间点重放。
4. **可审计**：所有状态变更与判定带全序序号落审计，越权不留痕也不改状态。
